# GraphRAG 检索方式总结与关键词检索的局限

> 记录时间：2026-08-19 ｜ 模块：后端 / GraphRAG

## 当前检索方式（两层）

### 第一层：关键词匹配（找种子节点）

纯 Python 字符串处理，零外部依赖：

```
用户 query → 去标点 → 空格分词 → 中文滑动窗口（1-4字）→ 停用词过滤 → 关键词列表
                                                                           │
                                                          ┌────────────────┘
                                                          ▼
                                          遍历每个节点，if keyword in node.label → 打分
                                                                           │
                                                          ┌────────────────┘
                                                          ▼
                                                    按得分排序取 topK = 种子节点
```

### 第二层：图遍历（邻居扩展）

从种子节点出发，沿边 BFS 扩展 1-2 跳，收集关联节点和边，裁剪子图。

### 多项目检索

遍历用户所有项目，分别执行上述两层，按匹配度排序取 top 3，汇总子图喂给 LLM。

## 关键词检索的四个问题

### 1. 没有分词能力，中文靠滑动窗口暴力枚举

因为没有 jieba 等分词库，中文句子"张三在哪个公司"无法拆成"张三 / 在 / 哪个 / 公司"，只能靠滑动窗口枚举所有 1-4 字子串。

**后果**：产生大量无意义噪音词（"三在"、"个公"、"在哪"），真正有用的关键词（"张三"、"公司"）淹没在噪音里。依赖停用词过滤，但停用词不可能覆盖所有无意义子串。

### 2. 只能做字符串包含匹配，无法做语义匹配

匹配逻辑是 `if keyword in node.label`——Python 的 `in` 操作符，纯字符串包含。

**后果**：

| 用户问 | 节点 label | 能匹配？ | 原因 |
|---|---|---|---|
| "张三" | "张三" | ✅ | 精确包含 |
| "张三" | "张三丰" | ✅ | 包含 |
| "张三先生" | "张三" | ❌ | "张三先生"不是"张三"的子串 |
| "那个科技公司" | "星辰科技" | ❌ | 语义接近但字面不同 |
| "P2024-001" | "P2024-001" | ✅ | 精确包含 |

语义相近但字面不同的词**完全匹配不上**。比如用户习惯说"科技公司"，图谱里存的是"星辰科技"，关键词匹配无能为力。

### 3. 得分规则过于简单

当前打分规则：label 命中 +10，type 命中 +5，properties 命中 +3。没有考虑：
- 关键词在 label 中的位置（开头匹配权重应更高）
- 关键词长度（长词匹配比单字匹配更有意义）
- 多个关键词命中的组合效应

"张三"命中"张三"得 10 分，"张"命中"张三"也得 10 分——但前者是精准匹配，后者只是一个单字包含。

### 4. 滑动窗口产生大量噪音，影响召回质量

滑动窗口 1-4 字枚举，一个 6 字句子产生约 20 个子串，其中有效关键词通常只有 2-3 个。大量噪音词参与匹配，增加了误匹配概率。

**例子**："张三在哪个公司" → 产生"三在"、"在哪"、"个公"等无意义词，某些可能碰巧命中节点 label（如"三在"命中"三在集团"），产生假阳性。

## 已识别的改进方向

| 方向 | 解决什么问题 | 怎么做 |
|---|---|---|
| **语义匹配（embedding）** | 问题 2：字面不同但语义相同 | 节点 label 做 bge-m3 embedding，跟 query 向量算余弦相似度 |
| **引入 jieba 分词** | 问题 1、4：滑动窗口噪音 | `pip install jieba`，一行 `jieba.cut` 替代滑动窗口 |
| **得分规则优化** | 问题 3：打分不精确 | 长词加权、前缀匹配加分、BM25 思想 |
| **混合检索** | 全部 | 关键词 + 语义两路召回，合并去重，互补盲区 |

## 建议优先级

**语义匹配（embedding）** 改动最小（复用 bge-m3），价值最高（直接解决"搜不到"的问题），且不依赖 jieba。关键词匹配保留作为精确匹配通道，语义匹配补上盲区，两路混合。然后再考虑是否引入 jieba 替换滑动窗口。
